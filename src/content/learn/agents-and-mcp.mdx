## 一句話解釋

<Term id="agent">AI Agent</Term> 是把<Term id="llm">大型語言模型</Term>放進一個「規劃、行動、觀察」的迴圈：模型自己決定下一步要用哪個工具、帶什麼參數，看了結果再決定下一步，直到完成任務。<Term id="mcp">MCP</Term>（Model Context Protocol，模型上下文協定）則是一套開放標準，讓搜尋、資料庫、檔案與各種企業系統只要包裝一次，就能接上所有支援 MCP 的 AI 應用。

## 生活化比喻

<Callout type="analogy" title="一位只能坐在座位上的天才實習生">

想像公司來了一位博學的實習生，但規定他只能坐在座位上，不能自己起身拿東西。他能做的，是在便條紙上寫「請幫我查客戶 A 上個月的訂單」，交給助理去辦；助理把結果拿回來，他讀完再寫下一張便條。

- **便條紙的固定格式**就是工具呼叫：寫清楚要用哪個工具、每一欄填什麼。
- **一張接一張地寫、讀、再寫**，直到把報告完成，就是 Agent 迴圈。
- **各部門的系統**原本插頭不同、操作手冊也不同，每接一套就要重新教一次。MCP 像是把全公司的設備換成同一種插座、同一種格式的說明書：新系統只要做成這種插座，每位實習生立刻都會用。
- **助理有權拒絕**：便條上寫「把公司帳戶的錢轉出去」，助理會先打電話問主管。這就是 Agent 的權限控管。

</Callout>

## 原理

### 第一步：模型怎麼「使用」工具？

語言模型本身只會輸出文字，不會真的上網或查資料庫。所謂「使用工具」，其實是一場分工，稱為 <Term id="function-calling">Function Calling</Term>（工具呼叫）：開發者先把可用的工具寫成說明書，包括名稱、用途，以及用 JSON Schema 定義的參數格式；模型判斷需要時，輸出一段格式固定的呼叫請求；真正執行的是外圍的應用程式。OpenAI 的開發文件把這個流程拆成五步<Cite k="openai-fc" />：

  title="一次工具呼叫的來回"
  steps={[
    { title: "附上工具清單", detail: "把問題連同工具說明書一起送給模型" },
    { title: "模型提出呼叫", detail: "輸出工具名稱與參數，而不是直接回答" },
    { title: "程式執行", detail: "應用程式依參數查資料或執行動作" },
    { title: "回傳結果", detail: "把工具的輸出再送回模型" },
    { title: "作答或再呼叫", detail: "資訊夠了就回答，不夠就呼叫下一個工具" }]}
/>

這個分工有兩個重要含意。第一，**模型只負責「決定」，程式負責「執行」**，所以權限可以在模型之外把關：程式可以拒絕某個呼叫，或先請人確認。Anthropic 的 <Term id="api">API</Term> 也是如此：模型回傳 tool_use 區塊，開發者的程式執行後，再以 tool_result 區塊送回<Cite k="claude-tools" />。第二，**工具說明書本身也要花錢**。工具定義會被放進系統訊息，占用<Term id="context-window">上下文視窗</Term>，並以輸入 <Term id="token">Token</Term> 計費<Cite k="openai-fc" />；以 Claude Opus 5.5 為例，只要提供工具（且採預設的自動選擇模式），API 就會先加入 286 個 Token 的工具系統提示，還不含各工具自己的說明<Cite k="claude-tools" />。

工具的種類很廣：搜尋、執行程式、查資料庫，連沒有 API 的舊系統，也能透過 <Term id="computer-use">Computer Use</Term> 看螢幕截圖、操作滑鼠鍵盤來使用。<LearnLink id="rag-and-vector-search">RAG</LearnLink> 的檢索步驟同樣可以做成工具，由模型自己決定要不要查、查什麼，這就是 <Term id="rag">RAG</Term> 的 Agent 化。

### 第二步：把工具呼叫放進迴圈，就成了 Agent

只呼叫一次工具，還只是「會查資料的聊天機器人」。把「想一想、做一步、看結果」反覆執行，才是 Agent。2022 年的 ReAct 論文讓模型交錯寫出推理與行動，每次行動後讀取環境回饋，再推理下一步；只給 1 到 2 個示範例子，ReAct 在文字版家務遊戲 ALFWorld 與模擬購物網站 WebShop 的任務成功率，就比模仿學習與強化學習方法分別高出 34 與 10 個百分點<Cite k="react" />。

### 上下文是 Agent 的工作記憶

Agent 每做一步，工具呼叫與結果都會附加到對話紀錄，下一輪再整份送進模型。上下文視窗因此很快被填滿，而且越長越難用：Anthropic 引述「大海撈針」類評測的研究指出，Token 數越多，模型從上下文中找回資訊的準確度越低，稱為「上下文腐化」（context rot）；原因之一是 <Term id="transformer">Transformer</Term> 中每個 Token 都要和其他 Token 建立關聯，n 個 Token 就有 n² 組關係<Cite k="context-eng" />。

所以「上下文工程」成了 Agent 設計的核心，常見三招<Cite k="context-eng" />：

- **壓縮**：快滿時把對話摘要成重點，用摘要重新開始；清掉舊的工具結果是最輕量的做法。
- **外部筆記**：讓 Agent 把進度寫到上下文以外的檔案，需要時再讀回來，等於長期記憶。
- **子 Agent**：把子任務交給另一個上下文乾淨的 Agent；它可能用掉數萬個 Token 探索，最後只回傳 1,000 到 2,000 個 Token 的摘要。

第三招就是「多 Agent」系統。Anthropic 的研究功能由一個主 Agent 規劃，再平行派出多個子 Agent 各查一個面向。內部評測中，這套系統比單一 Agent 的 Claude Opus 4 表現高出 90.2%，複雜查詢的研究時間最多縮短 90%；代價是 Token 用量大增<Cite k="multi-agent" />：

### MCP：替所有工具做一個通用插座

工具呼叫解決了「模型怎麼用工具」，卻沒有解決「工具怎麼接上模型」。2024 年 11 月 25 日，Anthropic 開源 MCP 時點出問題：每接一個新的資料來源，都要寫一套客製整合，系統很難擴大<Cite k="mcp-launch" />。假設有 M 個 AI 應用、N 個工具，彼此兩兩對接：

<MathTeX tex={"\\underbrace{M\\times N}_{\\text{各自對接}}\\;\\longrightarrow\\;\\underbrace{M+N}_{\\text{共用標準}}"} display label="沒有共同標準時要做 M 乘以 N 套整合，有了共同標準只需 M 加 N 套" />

例如 10 個 AI 應用、100 個工具，兩兩對接要 1,000 套整合；有了共同標準，每個應用實作一次用戶端、每個工具實作一次伺服器，只要 110 套。MCP 的設計也參考了讓各種程式編輯器共用語言支援的 Language Server Protocol<Cite k="mcp-spec" />。

MCP 的架構有三個角色<Cite k="mcp-arch" />：

- **Host（主程式）**：使用者面對的 AI 應用，例如聊天 App 或程式編輯器，負責管理連線、權限與使用者同意。
- **Client（用戶端）**：Host 內部的連接器，每個用戶端只對應一個伺服器。
- **Server（伺服器）**：把某種能力包成標準介面，可以是本機程式，也可以是遠端服務。

雙方以 JSON-RPC 2.0 格式交換訊息<Cite k="mcp-spec" />。伺服器能提供三種「原語」，差別在於由誰控制<Cite k="mcp-server" />：

| 原語 | 由誰控制 | 用途 | 例子 |
|---|---|---|---|
| Tools（工具） | 模型 | 讓模型執行動作或查詢 | 送出 API 請求、寫入檔案 |
| Resources（資源） | 應用程式 | 提供給模型參考的資料 | 檔案內容、Git 紀錄 |
| Prompts（提示範本） | 使用者 | 預先寫好的指令範本 | 斜線指令、選單項目 |

其中有一條設計原則特別重要：伺服器不能讀取整段對話，也不能「看進」其他伺服器，完整的對話紀錄只留在 Host 手上<Cite k="mcp-arch" />。第三方工具因此只拿得到完成任務所需的資訊。

**從 2024 到 2026：MCP 怎麼長大？** 推出約一年後，公開運作的 MCP 伺服器已超過 1 萬個，ChatGPT、Cursor、Gemini、Microsoft Copilot、Visual Studio Code 等產品都已支援，AWS、Cloudflare、Google Cloud 與 Microsoft Azure 也提供部署服務。2025 年 12 月，Anthropic 把 MCP 捐給 Linux 基金會旗下新成立的 Agentic AI Foundation（AAIF），由 Anthropic、Block 與 OpenAI 共同創立；首批專案還有 Block 的 goose 與 OpenAI 的 AGENTS.md<Cite k="aaif" />。AGENTS.md 是寫給程式 Agent 看的專案說明檔格式，已有超過 6 萬個開源專案採用<Cite k="agents-md" />。

**2026-07-28 版規格：改成「無狀態」。** MCP 仍在快速演進。2026 年 7 月 28 日定案的新版拿掉了協定層級的工作階段（session）與初始握手，每個請求都自帶協定版本與用戶端能力<Cite k="mcp-changelog" />。好處是任何一台伺服器都能處理任何一個請求，放在最簡單的負載平衡器後面就能擴充，不需要共享儲存，也更容易部署在無伺服器（serverless）平台上；需要跨呼叫保存狀態的工具，改由伺服器發一個「代號」，讓模型在後續呼叫中當成參數帶回來<Cite k="mcp-2026" />。新版也正式建立擴充框架：負責長時間任務的 Tasks 移出核心，和能在對話中顯示互動介面的 MCP Apps 等一樣，成為選用的擴充功能<Cite k="mcp-2026" />。

### A2A：Agent 與 Agent 之間的協定

MCP 處理的是「一個 Agent 接上工具」；當不同公司開發的 Agent 需要互相分工，就需要另一套語言。Google 在 2025 年 4 月 9 日發表 <Term id="a2a">A2A</Term>（Agent2Agent）協定，首發有 50 多家技術夥伴，定位為與 MCP 互補：每個 Agent 用一份 JSON 格式的「Agent Card」公開自己的能力，其他 Agent 讀了就知道該把哪項工作交給誰<Cite k="a2a-launch" />。A2A 在推出穩定的 1.0 版規格之後，於 2026 年 8 月以「成長階段」專案加入 AAIF，官方表示已有超過 150 個組織支持<Cite k="a2a-aaif" />。

### 工具越多越好嗎？Token 的帳要算清楚

接上的伺服器一多，問題就來了。Anthropic 在 2025 年 11 月指出，多數用戶端會在一開始就把所有工具定義載入上下文；開發者常讓 Agent 同時連接數十個 MCP 伺服器、數百甚至上千個工具，模型還沒讀到問題，就可能先處理數十萬個 Token。中間結果也一樣：要把一份 2 小時的會議逐字稿從雲端硬碟搬到客戶管理系統，逐字稿會流經模型兩次，可能多處理 5 萬個 Token<Cite k="code-exec" />。

解法之一是讓 Agent 寫程式來呼叫工具：把各個 MCP 伺服器包裝成程式庫，Agent 需要時才去讀取對應工具的說明，大量資料則留在程式執行環境裡處理，模型只看結果。在 Anthropic 的範例中，光是改成只載入需要的工具定義，Token 用量就從 15 萬降到 2,000，省下 98.7%；讀取一份 1 萬列的試算表時，也可以先在程式裡篩選，模型只需看 5 列<Cite k="code-exec" />。新版 MCP 規格也建議伺服器以固定順序列出工具，讓用戶端能快取工具清單，並提高<Term id="prompt-caching">提示快取</Term>的命中率<Cite k="mcp-changelog" />。

### 安全：會動手的 AI，風險也不同

聊天機器人出錯，頂多是答錯；Agent 出錯，可能是寄錯信、刪錯檔、洩漏資料。MCP 規格明白寫著：工具等於可以執行任意程式碼，必須謹慎對待，Host 在呼叫任何工具前都必須取得使用者明確同意<Cite k="mcp-spec" />；而且應該始終有人類在迴路中，能夠拒絕工具呼叫。伺服器附在工具上、描述其行為的註記（annotations），除非來自可信任的伺服器，否則一律視為不可信<Cite k="mcp-tools" />。

最大的威脅是<Term id="prompt-injection">提示注入</Term>：Agent 讀到的網頁、郵件或文件藏有惡意指令，模型誤以為是使用者的命令。軟體工程師 Simon Willison 在 2025 年 6 月提出「致命三要素」：一個 Agent 只要同時能存取私人資料、會接觸不可信的內容、又能對外傳送資訊，攻擊者就很容易誘騙它把私人資料送出去<Cite k="trifecta" />。MCP 讓使用者能自由混搭各家工具，反而可能在不知不覺中湊齊這三項；他也提醒，宣稱能攔下 95% 攻擊的防護產品，以資安標準來看仍是不及格<Cite k="trifecta" />。

因此實務上的防線是多層的：只開放任務需要的工具（最小權限）、把工具回傳的內容當成不可信的資料、付款或刪除等高風險動作一律先請人確認。MCP 規格也建議用戶端在呼叫前把工具的輸入顯示給使用者、設定逾時，並記錄每次工具使用以供稽核<Cite k="mcp-tools" />。

<DeepDive title="深入一點：一次 MCP 呼叫長什麼樣？Agent 的 Token 帳本怎麼算？">

**MCP 的兩則訊息。** 用戶端先用 tools/list 詢問伺服器有哪些工具，伺服器回傳每個工具的名稱、說明與參數格式；模型決定使用後，用戶端再送出 tools/call。以下是規格中的天氣查詢範例，省略了每個請求都必須附帶的版本與能力欄位<Cite k="mcp-tools" />：

```json
{ "jsonrpc": "2.0", "id": 2, "method": "tools/call",
  "params": { "name": "get_weather", "arguments": { "location": "New York" } } }
```

伺服器的回應中，content 欄位放著給模型讀的結果，isError 標示是否出錯。規格區分兩種錯誤：「工具名稱不存在」這類協定錯誤，模型比較難自行修正；「日期必須是未來」這類執行錯誤，則應回傳給模型，讓它調整參數再試一次<Cite k="mcp-tools" />。這正是 Agent 能自我修正的基礎。

**為什麼 Agent 這麼吃 Token？** 模型本身不記得上一輪，每一輪都要把整段紀錄重新送進去。假設系統提示加上工具說明共 s 個 Token，每一輪新增的呼叫與結果共 c 個 Token，跑 n 輪下來，累計送進模型的輸入 Token 數是：

<MathTeX tex={"T_{\\text{輸入}}=n\\,s+c\\,\\frac{n(n-1)}{2}"} display label="累計輸入 Token 數等於輪數乘以固定開銷，加上每輪新增量乘以 n 乘 n 減 1 再除以 2" />

第二項隨輪數的平方成長。試算：s = 5,000、c = 2,000、n = 30，累計輸入約 102 萬個 Token（固定開銷 15 萬，加上累積紀錄 87 萬）。以 Claude Opus 5.5 每百萬輸入 Token 4 美元計算，約 4.1 美元<Cite k="claude-pricing" />。

不過每一輪的開頭幾乎都和上一輪相同，正適合提示快取：Opus 5.5 的快取命中只收基本輸入價的 0.05 倍，也就是每百萬 Token 0.20 美元；寫入 5 分鐘快取則是每百萬 5 美元<Cite k="claude-pricing" />。若每輪只有新增的部分要寫入快取、其餘都命中，同一個任務的輸入費用約可降到 0.5 美元（試算，未含輸出 Token）。這也是規格建議工具清單維持固定順序的原因：順序一變，快取就失效。

**真實世界的提示越來越長。** OpenRouter 與 a16z 分析該平台逾 100 兆個 Token 的使用紀錄發現，平均提示長度從約 1,500 個 Token 增加到 6,000 個以上，程式相關請求常超過 2 萬個輸入 Token；程式類用量占比則從 2025 年初的約 11% 升到超過 50%<Cite k="openrouter" />。這與 Agent 反覆累積上下文的特性一致；不過這是單一平台的資料，企業內部與本地部署的用量不在統計範圍內<Cite k="openrouter" />。
