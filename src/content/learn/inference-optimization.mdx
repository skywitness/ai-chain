## 一句話解釋

推論最佳化，是在不降低（或幾乎不降低）回答品質的前提下，讓模型每產生一個 <Term id="token">Token</Term> 都更便宜、更快的一整套工程技巧。它們大多在對付同一個瓶頸：<Term id="decode">Decode</Term> 階段每產生一個 Token，都要把模型權重與累積的 <Term id="kv-cache">KV Cache</Term> 從 <Term id="hbm">HBM</Term> 搬一遍，<Term id="gpu">GPU</Term> 的運算單元卻大多在等資料。主要工具有四類：管好 KV Cache（少存、少重算、少浪費）、<Term id="quantization">量化</Term>（每個數字少用幾個位元）、<Term id="speculative-decoding">推測解碼</Term>（一次驗證好幾個 Token）、<Term id="disaggregated-inference">分離式推論</Term>（把兩個階段交給不同的硬體）。這些技巧疊起來，決定了推論業者的毛利，也決定資料中心要買什麼樣的晶片、記憶體與網路。

本文假設你已讀過<LearnLink id="training-vs-inference-economics">訓練與推論的經濟學</LearnLink>與<LearnLink id="memory-and-hbm">記憶體牆與 HBM</LearnLink>，知道推論成本為什麼取決於批次與記憶體頻寬；這裡把重點放在各種技巧的原理、實測數字與彼此的取捨。

## 生活化比喻

<Callout type="analogy" title="一間同時接幾千張單的中央廚房">

- **每出一道菜，都得把整本食譜從倉庫搬出來翻一遍**：這就是 Decode。真正下鍋的時間很短，時間都花在搬食譜（讀取權重）上。一次接很多張單、翻一次食譜就一起做（批次處理），最劃算。
- **每桌的點菜紀錄要放在手邊（KV Cache）**：不然每上一道菜，都得重問一次整桌點了什麼。但客人越多、坐得越久，檯面就越擠。把紀錄寫得精簡（GQA、MLA）、用活頁夾分頁收好（PagedAttention）、熟客的固定套餐直接沿用（前綴快取），都是在省檯面。
- **把精確到 0.01 克的配方，改成用量匙標示（量化）**：食譜變薄、翻得更快；只要量匙夠準，味道幾乎不變。
- **學徒先把接下來幾道菜擺好盤，主廚一眼檢查（推測解碼）**：對的直接出餐，從第一道錯的開始重做。主廚看一眼的時間，和自己做一道差不多。
- **把備料區和出餐線分開（分離式推論）**：備料（Prefill）一次處理大量食材，需要力氣；出餐（Decode）講求穩定快速。兩者擠在同一條線上，遇到大單備料，出餐就會卡住。

## 原理

### 先找瓶頸：兩個階段、兩種限制

一個請求會經過兩個階段。<Term id="prefill">Prefill</Term> 一次讀完整段提示詞，所有輸入 Token 可以平行計算，屬於大型矩陣乘法，GPU 的運算單元可以接近滿載；它決定使用者要等多久才看到第一個字，也就是 <Term id="ttft">TTFT</Term>（首 Token 延遲）。Decode 則一次只產生一個 Token，每一步都要把權重與 KV Cache 讀一遍，速度受記憶體頻寬限制；它決定之後每個字之間的間隔，DistServe 論文稱為 TPOT（每個輸出 Token 的時間）<Cite k="distserve" />。

用屋頂線（roofline）的角度看最清楚。以每秒浮點運算次數（<Term id="flops">FLOPS</Term>）計，H100 SXM 的 BF16 稠密算力約 989 TFLOPS，HBM 頻寬則是 3.35 TB/s<Cite k="h100" />，兩者相除約 295：每從記憶體讀 1 位元組，要做將近 300 次運算，運算單元才不會閒著（本站換算）。Decode 時每個參數以 2 位元組存放、只做一次乘法與一次加法，同時只服務一個請求時，每讀 1 位元組只做約 1 次運算，離 295 差了近 300 倍。

<Term id="batching">批次處理</Term>能救回權重這一半：讀一次權重、同時替 B 個請求各算一個 Token，運算強度就變成約 B。代價是批次越大，整體<Term id="throughput">吞吐量</Term>越高，每位使用者等下一個字的<Term id="latency">延遲</Term>卻可能變長，推論服務永遠在兩者之間取捨。另一個限制是 KV Cache 每個請求各自一份，批次再大也無法共用；上下文越長，KV Cache 的讀取量占比越高，這是長上下文推論特別貴的原因之一。Google 研究者在 5,400 億參數的 PaLM 上，分別量測了兩種極端：小批次生成時每個 Token 29 毫秒（用了 int8 權重量化），大批次處理輸入時的運算使用率達 76%<Cite k="pope-inference" />。

### KV Cache：用記憶體換運算

<Term id="attention">注意力機制</Term>要讓每個新 Token 回頭看前面所有 Token 的 Key 與 Value。如果每產生一個字都把它們重算一遍，運算量會隨長度急遽增加；KV Cache 把每個 Token 在每一層算出的 Key 與 Value 存起來，之後只需替新 Token 計算一次。代價是記憶體，每個 Token 要存的大小為：

<MathTeX tex={"\\text{KV}_{\\text{token}}=2\\times L\\times H_{\\mathrm{kv}}\\times d_{\\mathrm{head}}\\times b"} display label="每個 Token 的 KV Cache 大小，等於 2（Key 與 Value）乘以層數 L、KV 頭數、每個頭的維度，再乘以每個數字的位元組數 b" />

以 Llama 3.1 70B 為例：80 層、64 個查詢頭、8 個 KV 頭，模型維度 8,192，每個頭的維度是 128<Cite k="llama3" />。以 BF16（2 位元組）存放，每個 Token 的 KV Cache 為 2 × 80 × 8 × 128 × 2 = 327,680 位元組，約 320 KB；一段用滿 128K（131,072 個 Token）的對話就要約 43 GB，而模型權重本身約 140 GB（本站換算）。如果每個查詢頭都保留自己的 Key 與 Value（64 個 KV 頭），每個 Token 會變成約 2.5 MB，同樣一段對話要 344 GB，是權重的 2.5 倍。

早期的推論系統還浪費了大半空間。vLLM 論文以 130 億參數的 OPT 模型為例，算出每個 Token 的 KV Cache 就要 800 KB；而實測既有系統時，因為記憶體碎片與預留過多，只有 20.4% 到 38.2% 的 KV Cache 空間真正存放了 Token 資料<Cite k="vllm" />。

縮小 KV Cache 的主線，是讓多個注意力頭共用 Key 與 Value：

- **MQA（多查詢注意力）**：Noam Shazeer 在 2019 年提出，所有注意力頭共用同一組 Key 與 Value，大幅減少逐步解碼時要搬運的資料，解碼快很多，品質只略為下降<Cite k="mqa" />。
- **GQA（分組查詢注意力）**：2023 年的折衷方案，把查詢頭分成幾組、每組共用一組 Key 與 Value。品質接近一般的多頭注意力，速度與 MQA 相當；既有模型只要再用原本預訓練約 5% 的運算量就能改造<Cite k="gqa" />。Llama 3 就以 8 個 KV 頭的 GQA 縮小 Decode 時的 KV Cache<Cite k="llama3" />。
- **MLA（多頭潛在注意力）**：<CompanyChip id="deepseek" /> 在 2024 年 5 月的 DeepSeek-V2 提出，把 Key 與 Value 壓縮成一個低維度的潛在向量，只快取這個向量。與自家前代 DeepSeek 67B 相比，KV Cache 減少 93.3%，最大生成吞吐量提高到 5.76 倍；論文指出它的快取量只相當於 2.25 組的 GQA，表現卻比一般多頭注意力更好<Cite k="deepseek-v2" />。DeepSeek-V3 每層每個 Token 只需存 512 + 64 = 576 個數字<Cite k="deepseek-v3" />，以 BF16 計，61 層合計約 69 KB，比只有其 1/10 大小的 Llama 3.1 70B 還小（本站換算）。

到了百萬 Token 的上下文，連 MLA 都不夠。2026 年 4 月的 DeepSeek-V4 改用混合了壓縮稀疏注意力與高度壓縮注意力的架構，官方表示在 100 萬 Token 的情境下，V4-Pro 每個 Token 的推論運算量只需 DeepSeek-V3.2 的 27%，KV Cache 只需 10%<Cite k="deepseek-v4" />。滑動視窗、線性注意力等其他做法，見<LearnLink id="transformer-and-attention">Transformer 與注意力機制</LearnLink>。

### 不浪費、不重算：分頁、連續批次與前綴快取

KV Cache 縮小之後，還要管得好。這一層的技巧多半做在<Term id="inference-engine">推論引擎</Term>裡：

- **分頁管理（PagedAttention）**：vLLM 借用作業系統虛擬記憶體的分頁概念，把 KV Cache 切成固定大小的區塊、用到才配置，不必占用連續空間，浪費接近零，還能讓不同請求共用相同的區塊。在相同延遲下，吞吐量比 FasterTransformer、Orca 等系統高 2 到 4 倍<Cite k="vllm" />。
- **連續批次（迭代層級排程）**：傳統做法要等一整批請求都寫完才換下一批，短回答只能乾等長回答。2022 年的 Orca 改成每跑完一次迭代就重新排班，寫完的請求立刻離開、新請求立刻加入；在 GPT-3 175B 上，相同延遲下的吞吐量是 NVIDIA FasterTransformer 的 36.9 倍<Cite k="orca" />。vLLM 論文也指出，Orca 的迭代層級排程與 PagedAttention 是互補的技術：前者讓更多請求能同時處理，後者讓記憶體裝得下更多請求<Cite k="vllm" />。
- **前綴快取**：許多請求的開頭一模一樣，例如系統提示詞、同一份文件、多輪對話的歷史，或 <Term id="agent">Agent</Term> 每一步都要帶上的工具說明。只要把這段前綴的 KV Cache 留下來，下一個請求就能跳過這部分的 Prefill。SGLang 以 RadixAttention 用樹狀結構管理可重用的 KV Cache，在 Agent 控制、少樣本學習、多輪對話等任務上，吞吐量最高為既有系統的 6.4 倍<Cite k="sglang" />。

前綴快取在真實服務中的效果相當可觀。DeepSeek 公布的 24 小時統計中，6,080 億個輸入 Token 有 56.3% 命中存放在磁碟上的 KV Cache；當時 DeepSeek-R1 的定價，快取命中的輸入每百萬 Token 0.14 美元，未命中則要 0.55 美元<Cite k="deepseek-infer" />。Anthropic 的<Term id="prompt-caching">提示快取</Term>也有類似的價差：讀取快取的價格是一般輸入的 0.1 倍（部分模型更低），寫入 5 分鐘有效的快取則是 1.25 倍<Cite k="anthropic-cache" />。

快取要放在哪裡，也成了硬體問題。NVIDIA 把 KV Cache 的存放位置分成四層：G1 是 GPU 的 HBM，放正在生成中的熱資料；G2 是主機的 <Term id="dram">DRAM</Term>；G3 是本機 <Term id="ssd">SSD</Term>；G4 是共享儲存。以 BlueField-4 驅動的 CMX 平台，則在 G3 與 G4 之間加入一層「G3.5」：以乙太網路連接、專為 KV Cache 最佳化的快閃記憶體層，NVIDIA 稱它的每秒 Token 數與能源效率都最多是傳統儲存的 5 倍<Cite k="nv-cmx" />。月之暗面的 Mooncake 走的也是類似路線，把 GPU 叢集裡閒置的 CPU、DRAM 與 SSD 組成分離式的 KV Cache 池<Cite k="mooncake" />。

### 注意力本身也要省搬運：FlashAttention

Prefill 與長上下文的注意力運算，同樣卡在搬資料。標準做法會把一個「每個 Token 對每個 Token」的大矩陣寫回 HBM 再讀出來；<Term id="flash-attention">FlashAttention</Term> 把運算切成小塊，在晶片內的 <Term id="sram">SRAM</Term> 裡一次做完，大幅減少 HBM 的讀寫，而且結果完全精確，不是近似。它在 GPT-2 上帶來 3 倍的訓練加速<Cite k="flashattention" />；針對 H100 改寫的 FlashAttention-3，以 FP16 計算時最高達 740 TFLOPS（約 75% 使用率），以 FP8 計算時接近 1.2 PFLOPS<Cite k="flashattention3" />。

Decode 的速度上限，大致由每一步要讀多少位元組決定。把權重從 16 位元壓到 8 位元，要搬的資料減半，小批次時的速度上限就接近翻倍，需要的 GPU 數也跟著減少。量化可以只壓權重，也可以連同啟用值與 KV Cache 一起壓，越激進越省，風險也越高。

- **事後量化**：2022 年的 LLM.int8() 讓 1,750 億參數的模型直接轉成 8 位元整數使用，記憶體減半而表現不降，關鍵是把少數數值特別大的「離群」維度留在 16 位元計算<Cite k="llm-int8" />。同年的 GPTQ 只花約 4 個 GPU 小時，就把 1,750 億參數模型的權重壓到 3 或 4 位元，準確度損失可忽略，首次能在單顆 GPU 上推論；端到端推論在 A100 上比 FP16 快約 3.25 倍<Cite k="gptq" />。
- **硬體原生的低精度格式**：Hopper 世代支援 <Term id="fp8">FP8</Term>。<CompanyChip id="meta" /> 以 FP8 推論 Llama 3 405B 時，只量化約占推論運算時間一半的前饋網路，注意力層與第一、最後一層維持較高精度；以 10 萬筆回答的獎勵模型分數比對，影響可忽略，Prefill 吞吐量最多提高 50%<Cite k="llama3" />。Blackwell 世代再支援 <Term id="fp4">FP4</Term>：MXFP4 每 32 個數值共用一個 2 的冪次縮放因子；NVIDIA 的 NVFP4 改為每 16 個數值共用一個 FP8 縮放因子，平均約 4.5 位元，記憶體約為 FP16 的 1/3.5。NVIDIA 把 DeepSeek-R1-0528 從 FP8 量化到 NVFP4，主要任務的準確度下降在 1% 以內<Cite k="nvfp4" />。
- **量化感知訓練**：與其訓練完再壓縮，不如在訓練時就讓模型適應低精度。<CompanyChip id="openai" /> 的 gpt-oss-120b 在後訓練階段就把 MoE 權重量化為 MXFP4，因此能放進單張 80 GB GPU<Cite k="gptoss-card" />。<CompanyChip id="moonshot-ai" /> 指出，<Term id="reasoning-model">推理模型</Term>的解碼長度很長，量化常造成明顯退步，因此 Kimi K2 Thinking 在後訓練階段就對 MoE 權重做 INT4 量化感知訓練，生成速度約提高 2 倍，所有評測也都在 INT4 下取得<Cite k="kimi-k2-thinking" />；Kimi K3 更從 SFT 階段起就以 MXFP4 權重、MXFP8 啟用值訓練<Cite k="kimi-k3" />。DeepSeek-V4 的 MoE 專家參數也直接以 FP4 發布<Cite k="deepseek-v4" />。

量化不是免費的。月之暗面的經驗顯示，解碼長度很長的思考模型特別容易被量化誤差拖累；不同模型、不同任務對精度的敏感度也不一樣，部署前仍需要在自己的任務上驗證。

### 推測解碼：先猜再驗

Decode 受頻寬限制，代表大模型一次「驗證」好幾個 Token 的成本，跟產生一個 Token 差不多：權重反正都要讀一遍。推測解碼利用這一點，讓一個便宜的草稿機制先猜，再由大模型一次驗收。

關鍵在「修正過的拒絕取樣」：它保證最終輸出的機率分布與大模型自己逐字產生完全相同，所以是不犧牲品質的加速。Google 研究者 2022 年的論文在 T5-XXL 上達到 2 到 3 倍加速且輸出完全相同<Cite k="leviathan" />；DeepMind 在 700 億參數的 Chinchilla 上達到 2 到 2.5 倍<Cite k="chen-spec" />。Google 後來表示，推測解碼已用在多項產品中，讓 Google 搜尋的 AI 摘要在品質不變下更快產生<Cite k="google-spec" />。

草稿不一定要另一個模型。Medusa 在原模型上加幾個額外的預測頭，加速 2.2 到 3.6 倍<Cite k="medusa" />；EAGLE-3 最高可達 6.5 倍<Cite k="eagle3" />。DeepSeek-V3 則在訓練時就加入「多 Token 預測」（MTP），讓模型順便預測下一個之後的 Token；這個額外預測的接受率在 85% 到 90% 之間，解碼速度因此提高為 1.8 倍<Cite k="deepseek-v3" />，DeepSeek-V4 也保留了一層 MTP<Cite k="deepseek-v4" />。概念上，這和用小模型模仿大模型的<Term id="distillation">蒸餾</Term>相通：草稿越像大模型，猜中率越高。

推測解碼也有極限。批次很大時，GPU 已接近算力上限，多驗證的 Token 不再免費，加速幅度通常會縮小：EAGLE-3 在 SGLang 中、批次大小 64 時的吞吐量提升為 1.38 倍<Cite k="eagle3" />。

### 分離式推論：把備料區和出餐線分開

傳統的推論服務讓同一組 GPU 同時跑 Prefill 與 Decode。問題是兩者互相干擾：一個長提示詞的 Prefill 進來，正在 Decode 的請求就得等；兩個階段的資源配置與平行策略也被綁在一起，只能為了同時滿足 TTFT 與 TPOT 而多買硬體<Cite k="distserve" />。分離式推論把兩個階段交給不同的機器：

學術界的結果相當一致。DistServe 在 90% 以上請求符合延遲要求的前提下，可服務的請求量最多提高 7.4 倍<Cite k="distserve" />。<CompanyChip id="microsoft" /> 的 Splitwise 指出，Token 生成階段用不到最新 GPU 的算力，可以改用較低功耗、較便宜的硬體；拆開後可在成本低 20% 下達到 1.4 倍吞吐量，或在相同成本與功耗下達到 2.35 倍<Cite k="splitwise" />。代價是多了一段 KV Cache 的跨機器傳輸，必須仰賴 <Term id="rdma">RDMA</Term> 這類高速網路。

業界很快跟進。月之暗面的 Mooncake 是 Kimi 的服務平台，在真實負載下讓 Kimi 多處理 75% 的請求<Cite k="mooncake" />；DeepSeek 的線上服務同樣採 Prefill／Decode 分離<Cite k="deepseek-infer" />。<CompanyChip id="nvidia" /> 在 2025 年 3 月推出開源的 Dynamo 推論框架，把分離式服務與跨數千顆 GPU 的 KV Cache 管理做成通用元件，支援 vLLM、SGLang 與 TensorRT-LLM；NVIDIA 稱在 GB200 NVL72 叢集上執行 DeepSeek-R1 時，每顆 GPU 產生的 Token 數提高 30 倍以上，這是綜合多項最佳化與新硬體的廠商數字<Cite k="dynamo" />。

下一步是連硬體都分家。NVIDIA 的 Groq 3 LPX 機櫃有 256 顆 LPU、合計 128 GB 的晶片內 SRAM，頻寬 40 PB/s；與 Vera Rubin NVL72 搭配時，Rubin GPU 負責 Prefill 與 Decode 階段的注意力運算（需要大容量 HBM 存放 KV Cache），LPX 負責對延遲敏感的前饋網路與 <Term id="moe">MoE</Term> 專家運算，也可以擔任推測解碼的草稿引擎<Cite k="lpx-inside" />。LPX 在 2026 年 8 月宣布全面量產，以 10 萬 Token 上下文執行 Gemma 4 31B 時，在 Artificial Analysis 測試中達到每秒 3,400 個輸出 Token<Cite k="lpx-pr" />。MoE 為什麼特別適合這樣拆，見<LearnLink id="mixture-of-experts">混合專家模型深入</LearnLink>。

<DeepDive title="深入一點：屋頂線、KV Cache 的運算強度，與推測解碼的期望值">

**屋頂線模型。** 一段程式能達到的效能，等於「峰值算力」與「記憶體頻寬 × 運算強度」兩者中較小的那個；運算強度是每讀 1 位元組做幾次運算：

<MathTeX tex={"P=\\min\\left(P_{\\mathrm{peak}},\\;BW\\times I\\right),\\qquad I^{*}=\\frac{P_{\\mathrm{peak}}}{BW}\\approx\\frac{989\\ \\mathrm{TFLOPS}}{3.35\\ \\mathrm{TB/s}}\\approx 295"} display label="可達效能 P 等於峰值算力與頻寬乘以運算強度兩者的較小值；H100 的轉折點約為每位元組 295 次運算" />

運算強度低於 295，H100 就受頻寬限制<Cite k="h100" />。

**權重與 KV Cache 的不同命運。** Decode 時，權重被批次裡的 B 個請求共用，運算強度約為 B；KV Cache 卻只屬於單一請求。以 GQA 的 Llama 3.1 70B 為例，每個 KV 頭被 8 個查詢頭共用，讀進來的每個數值大約只做 8 次乘加，換算運算強度約為 8，而且不會因批次變大而提高（本站推算）。所以批次可以把權重的部分推向算力上限，長上下文的注意力運算卻始終受頻寬限制，這正是 GQA、MLA 與 KV Cache 量化持續有價值的原因，也是 NVIDIA 把注意力留在大容量 HBM 的 GPU、把前饋網路交給 LPU 的背景<Cite k="lpx-inside" />。

**推測解碼的期望值。** 假設每個猜測被接受的機率為 α、每輪猜 γ 個 Token，每輪大模型前向一次，預期能前進的 Token 數為<Cite k="leviathan" />：

<MathTeX tex={"\\mathbb{E}[\\text{tokens}]=\\frac{1-\\alpha^{\\gamma+1}}{1-\\alpha}"} display label="每輪預期產生的 Token 數，等於一減 alpha 的 gamma 加一次方，再除以一減 alpha" />

α = 0.8、γ = 4 時，每輪約前進 3.4 個 Token。DeepSeek-V3 的 MTP 相當於每輪只猜 1 個（γ = 1）、接受率 85% 到 90%，代入得每輪 1.85 到 1.9 個 Token，與實測的 1.8 倍速度相當接近；差距來自草稿與驗證本身的額外開銷（本站推算）<Cite k="deepseek-v3" />。
